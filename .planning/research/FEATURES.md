# Feature Research

**Domain:** строка «about» / версионный футер в однофайловой HTML-демке (калькулятор) внутри конфигурационного скелета OpenCode V2
**Researched:** 2026-10-25
**Confidence:** HIGH (по конвенциям футеров/semver — устоявшаяся практика; веб-поиск был недоступен, источники — общепринятые стандарты, перечислены внизу)

## Feature Landscape

### Table Stakes (Users Expect These)

Минимум, без которого about-line выглядит недоделанной или непроверяемой в этом репозитории.

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| Имя приложения в футере | Футер без названия не опознаваем; в `calculator.html` пока нет футера вовсе (есть только `<title>Калькулятор</title>`) | LOW | Можно взять название из `<title>` — «Калькулятор»; текст хардкодится, HTML-экранирование тривиально |
| Номер версии (semver-вид) | «v1.0.0» рядом с именем — стандарт де-факто; без версии строка «о себе» теряет смысл | LOW | Статическая строка-константа в JS/HTML; semver.org рекомендует `MAJOR.MINOR.PATCH`. Одно место определения — одна точка правды |
| Стабильная разметка (семантический `<footer>` + селектор) | Milestone требует структурного теста и UI e2e — тесты не могут надёжно цепляться за произвольный `<div>` | LOW | `<footer class="app-footer">` (или `data-testid`) → селектор для `tests/structure.test.js` и `tests/ui/calculator.spec.js` |
| Сдержанный вид (мелкий, приглушённый текст) | Футер не должен конкурировать с кнопками калькулятора; так делают во всех мелких демо | LOW | 1–3 строки CSS прямо в однофайловой разметке, без внешних зависимостей |

### Differentiators (Competitive Advantage)

Не обязательны, но делают фичу «настоящей» при почти нулевой цене.

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| Ссылка на исходный код (GitHub-репозиторий) | Обычная практика open-source футеров (`name vX — source`); репозиторий известен: `github.com/HeleonoraQA/my-opencode-project.git` | LOW | `<a href target="_blank" rel="noopener">`; работает и в file://, и под статическим сервером |
| Доступность (`role="footer"`/`aria-label`, контраст) | Дешёвый плюс к качеству: `<footer>` уже семантичен; aria-label помогает e2e-проверке видимости | LOW | Достаточно aria-label вида «О приложении»; контраст проверяется визуально, автоматический audit не нужен |
| Кросс-ссылка в документации | Включено в план (фаза 2): README/docs/memory упоминают фичу — git-хуки и конвенции репозитория требуют синхронизации доков | LOW | Только текстовая документация, код не затрагивается |
| Версия как единственная константа | Если JS использует версию где-то ещё сегодня — должна быть одна константа; исключает рассинхронизацию | LOW | Уточнить при планировании: в текущем файле версии нет, поэтому конфликтов не ожидается |

### Anti-Features (Commonly Requested, Often Problematic)

Кажутся «правильно rich», но ломают простоту демки или тесты.

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| Дата сборки в футере | Выглядит информативно | Нестабильный вывод ломает структурные/e2e-тесты при каждом прогоне; требует шага сборки, которого в проекте нет; с течением времени становится ложной информацией | Только статичная версия; дату можно держать в docs при релизе, не в разметке |
| Динамическая версия из `package.json` / CI-инъекция | «Не забыть обновить» | Однофайловая HTML-демка живёт вне build-пайплайна; инъекция требует тулинга и меняет CI — вне scope этого эксперимента | Хардкод версии рядом с именем + ручной bump при релизах (одна строка, один файл) |
| Интерактивный футер (кнопка «珍藏/changelog/About», модалка) | Объяснение версии по клику | Существенное усложнение разметки и новых UI-тестов ради отсутствующего читателя демки | Ссылка на репозиторий/доки вместо модалки |
| Авто-синхронизация версии с git-тегом / npm-script | Гарантия актуальности | Изменения скриптов и CI выходят за рамки изолированной мини-фичи (Explicit Out of Scope в PROJECT.md) | Конвенция «bump перед коммитом», закреплённая в docs |
| Лицензионный блок в футере | Юридическая тяжесть | Репозиторий-скелет не заявляет лицензию; дублирует проблему, которую надо решать на уровне репозитория, а не демки | Отложить до решения о лицензии всего репозитория |

## Feature Dependencies

```
[Стабильный селектор разметки]
    └──используется──> [Структурный тест] 
                       [UI e2e: видимость футера]

[Имя + версия (контент)] ──нужно раньше──> [Стабильный селектор]
                                           [Структурный тест]

[Ссылка на источник] ──enhances──> [Имя + версия]

[Дата сборки / инъекция версии из CI] ──conflicts──> [Структурный тест / UI e2e]

[Обновление документации] ──depends on──> [Финальная разметка + версия]
```

### Dependency Notes

- **Тесты требуют контента и селектора:** структурный тест и UI e2e не осмысленны, пока нет финального текста (`name v-version`) и предсказуемого селектора; значит разметка фиксируется в фазе 1 до/вместе с тестами, а дополнения (ссылка) не должны менять селектор.
- **Docs зависят от финализированной разметки:** фаза 2 обновляет README/docs точно так, как тесты ожидают разметку — следовательно, текст футера должен быть финальным к концу фазы 1.
- **Немонотонный контент конфликтует с тестами:** дата сборки/динамическая версия делают assertion нестабильным — эта зависимость определяет anti-feature-статус.

## MVP Definition

### Launch With (v1)

Minimum viable — ровно то, что закрывает Active-requirements PROJECT.md.

- [ ] Семантический `<footer>` в `calculator.html` — CarProveedor для всех тестов (stable selector)
- [ ] Текст «Калькулятор v1.0.0» — имя + версия, единственный обязательный контент
- [ ] Структурный тест (`tests/structure.test.js`) — что футер присутствует и содержит имя + версию
- [ ] UI e2e (`tests/ui/calculator.spec.js`) — футер видим пользователю
- [ ] Обновление README/docs/memory — синхронизация документации по конвенции репозитория

### Add After Validation (v1.x)

- [ ] Ссылка на репозиторий в футере — если хочется подчеркнуть open-source-происхождение (когда DOCS за что пусть)
- [ ] `aria-label`/уточнения доступности — при первом ревью a11y

### Future Consideration (v2+)

- [ ] Одно место определения версии, переиспользуемое кодом — если в калькуляторе появится логика, чувствительная к версии
- [ ] Лицензионная строка — только после решения о лицензии всего репозитория

## Feature Prioritization Matrix

| Feature | User Value | Implementation Cost | Priority |
|---------|------------|---------------------|----------|
| Имя приложения в футере | HIGH | LOW | P1 |
| Версия (semver-формат, статичная) | HIGH | LOW | P1 |
| Семантический `<footer>` + стабильный селектор | HIGH (для тестов) | LOW | P1 |
| Сдержанный CSS | MEDIUM | LOW | P1 |
| Ссылка на репозиторий | MEDIUM | LOW | P2 |
| aria-label / a11y-уточнения | MEDIUM | LOW | P2 |
| Кросс-обновление документации | MEDIUM (конвенция) | LOW | P1 (фаза 2) |
| Дата сборки | LOW | MEDIUM | — (anti-feature) |
| Инъекция версии из package.json/CI | LOW | HIGH | — (anti-feature) |

**Priority key:**
- P1: Must have for launch
- P2: Should have, add when possible
- P3: Nice to have, future consideration

## Competitor Feature Analysis

«Конкуренты» здесь — типовые варианты about-line в похожих веб-демо и конфиг-скелетах.

| Feature | Типовая однофайловая демка | Типовой open-source проект (футер/README) | Our Approach |
|---------|---------------------------|-------------------------------------------|--------------|
| Имя | Часто отсутствует или только `<title>` | Название + описание | Хардкод «Калькулятор» в футере |
| Версия | Иногда, захардкожена | Semver, из релизов/тегов | Статичный semver «v1.0.0», ручной bump |
| Ссылка на источник | Редко | Стандарт | v1.x: `<a>` на GitHub |
| Дата сборки | Редко, у «генерированных» страниц | Только в changelog/release notes | Не делаем |
| Лицензия | Редко | Стандарт | Не делаем (вне scope) |
